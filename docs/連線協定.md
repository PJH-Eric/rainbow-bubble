# 彩虹泡泡砲 連線協定

伺服器：`server.js`（HTTP ＋ `/ws` WebSocket，文字訊息、每則一個 JSON 物件、欄位 `type` 是訊息名稱）。
伺服器是裁判，對局規則全部走 `public/js/match.js`；客戶端只負責「送輸入、重播事件」。
單則訊息上限 4000 字元（超過會被忽略）；連線上限由 `lib/ws.js` 控制（64 KB）。

## 1. 連線與身分

```
client → { type:'hello', key, name, dragon }     連上後 5 秒內必須先送；key 為 8～64 字元 [A-Za-z0-9_-]
server → { type:'welcome', key, pid, name, dragon, serverNow, room }
```

- `key`：瀏覽器自己產生並存在 localStorage 的身分；同一個 key 再連線，舊連線會收到 `{type:'replaced'}` 並被關閉（不要自動重連）。
- `pid`：伺服器發的數字 id（踢人、聊天用）。`name` 最多 10 個字（會消毒）。`dragon` 是 `Art.DRAGONS` 的 id：
  `rainbow cloud candy sun moon blossom frost forest`。同房間內龍不會重複，搶到同一隻會被換成空著的。
- `room`：重連時若原本在房間內，直接帶房間檢視（見 §3），之後還會收到 `chatlog`；若對局進行中還會收到 `start`＋`sync`（見 §5）。沒在房間則收到 `rooms`。
- 心跳：`ping{t}` → `pong{t}`（原樣回 t）。伺服器另有 WebSocket 層 ping，45 秒沒反應會踢線。
- 斷線寬限 30 秒：寬限內用同一個 key 重連，席位與對局都保留；超過 30 秒視為離場。

## 2. 大廳

| 方向 | 訊息 | 欄位 / 說明 |
|---|---|---|
| C→S | `lobbySub` | 要求最新 `rooms`（停在大廳的連線，列表變動時伺服器也會主動推） |
| S→C | `rooms` | `rooms:[{id,name,phase,max,players,humans,ais,spectators,host,settings,full,joinable}]`，只列 `publicRoom=true` 的房間。`players` = 已佔席位（真人＋電腦），`humans`／`ais` 分開計；`full`／`joinable` 以 `players` 判斷 |
| C→S | `profile` | `{name,dragon}`：更新暱稱／龍（在房間內且 phase='room' 時同步到席位） |
| C→S | `create` | `{name,dragon,roomName,max?,settings?}`：建立房間並成為房主。`max` 為 2..4；`settings` 為 §4 的 patch（可省略） |
| C→S | `quick` | `{name,dragon}`：加入人數最多的公開、可加入房間；沒有就自己開一間（`joined.note` 會說明） |
| C→S | `join` | `{room, as:'player'\|'spectator', name, dragon, token?}`；帶 `token` 時角色由邀請決定，`as` 被忽略 |
| S→C | `joined` | `{room, role:'player'\|'spectator', note}`：`note` 非空時代表被降級成觀戰（對局中／席位已滿） |
| S→C | `joinFailed` | `{reason}`：`invalid`（找不到／token 錯）、`revoked`、`expired`、`closed`（房間已關閉） |
| S→C | `error` | `{code,text}`：`banned` `spec_full` `spec_off` `full`（席位含電腦已滿）`max` `few` `offline` `notready` |

房間代碼是 4 個大寫字母（例 `KMQR`）。

## 3. 房間

```
S→C { type:'room', room: RoomView | null }       任何變動都會對房內每個人各送一份（內容含「你」的視角）；null = 你已不在任何房間
```

`RoomView`：

```js
{
  id, name,
  phase: 'room' | 'countdown' | 'playing',      // room=房間（含上一局結束後）；countdown=倒數 3 秒；playing=對局中
  max,                                            // 席位數 2..4
  hostSeat,                                       // 房主的座位 index
  settings: { mode, level, layout, theme, duration, publicRoom, allowSpectators },
  seats: [ { i, kind:'human'|'ai'|'empty', name, dragon, ready, connected, host, pid, slot, aiLevel? } ],   // 長度 = max；slot 只在對局中有值（該座位的 Match slot）
                                                  // kind='ai'：電腦席位，aiLevel='baby'|'easy'|'normal'|'hard'，ready/connected 恆為 true，pid=null
  spectators: [ { pid, name } ], specCount, specCap: 20,
  you: { pid, role:'player'|'spectator', seat, host },     // seat = -1 代表觀戰
  humans, ais,                                    // 真人席位數、電腦席位數（humans+ais ≤ max ≤ 4）
  canStart,                                       // 房主視角有用：席位（真人＋電腦）≥2、真人全部在線、非房主的真人都已準備（電腦自動準備）
  invites: [ { token, role, created } ]           // 只有房主會收到：目前有效的邀請
}
```

| 方向 | 訊息 | 說明 |
|---|---|---|
| C→S | `leave` | 離開房間（或不再觀戰） |
| C→S | `ready` | `{value:true\|false}`：非房主、phase='room' 才有效 |
| C→S | `sit` | 觀戰者入座（phase='room'、有空位） |
| C→S | `watch` | 玩家改觀戰（phase='room'；房主不行） |
| C→S | `start` | 房主開始（見 §5）。錯誤碼：`few` `offline` `notready` |
| C→S | `rematch` | 任何坐著的玩家：「我想再來一局」。非房主 → 自動設為準備好；房主 → 只在聊天室廣播。對局結束後 0.5 秒內送也算（回房間時套用） |
| C→S | `settings` | `{patch}`：房主、phase='room'（見 §4）。成功後所有人的 `ready` 清掉 |
| C→S | `addAI` | `{level?}`：房主、phase='room'：把一個空位變成電腦席位（等級 `baby｜easy｜normal｜hard`，缺省或不合法 → `easy`）。名字比照單機「花花・電腦」（隨機一隻沒被用的龍的名字去掉「龍」＋「・電腦」），龍與其他席位不重複，自動準備好。真人＋電腦合計不能超過 `max`，滿了回 `error full`。聊天室會有一則系統訊息 |
| C→S | `setAI` | `{seat, level}`：房主、phase='room'：改某個電腦席位的等級 |
| C→S | `removeAI` | `{seat}`：房主、phase='room'：移除電腦席位（變回空位，可讓真人入座）。對真人席位無效 |
| C→S | `kick` | `{seat}` 或 `{pid}`：房主踢人（只對真人；電腦請用 `removeAI`）。被踢者收到 `{type:'kicked',text}`，並且不能再進同一個房間 |
| C→S | `chat` | `{text}`：最多 60 字，同一人 450 ms 內只收一則 |
| S→C | `chat` | `{m:{pid,name,text,role:'player'\|'spectator'\|'sys',t}}`（`sys` 為系統訊息，pid=0） |
| S→C | `chatlog` | `{msgs:[m...]}`：進房／重連時的最近 40 則 |
| C→S | `invite` | `{role:'player'\|'spectator'}`：房主產生邀請 → 房主收到 `{type:'invite',room,token,role}` |
| C→S | `revoke` | 房主撤銷「所有」邀請 |
| C→S | `inviteInfo` | `{room,token}`：查詢邀請（不會入房）。回 `inviteInfo`：`{ok:false,reason}` 或 `{ok:true,room,name,role,phase,players,max,full,willSpectate}` |
| S→C | `closed` | `{text,room}`：房間關閉（見下）。同時會收到 `room:null` 與 `rooms` |
| S→C | `replaced` | 同 key 在別處連線，這條被取代 |

- 邀請 token 12 字元、24 小時有效、可撤銷。邀請連結建議格式：`?room=KMQR&t=<token>`（由前端自訂）。
- **房間自動關閉**：座位上的**真人**降到 0（離開、被踢、斷線超過 30 秒）→ 立刻關閉：邀請全部失效、對局停止、電腦停止出手（brain 清除，不留計時器）、全員收到 `closed`。觀戰者與電腦席位都不算真人。已關閉的房間不會因為重連復活（`join` 回 `joinFailed{reason:'closed'}`，保留 1 小時）。
- 房主離開 → 依座位順序由下一位**真人**接任（`ready` 清掉；不會交給電腦）。
- 席位上限 4 含電腦：真人＋電腦坐滿時，邀請／`join` 的新玩家會變成觀戰者（`joined.note`），房主移除一個電腦後觀戰者可 `sit`。`maxPlayers` 不能低於目前所有已佔席位（真人＋電腦）。
- 重來一局：回到房間後電腦席位保留（等級不變、仍是準備好），房主可直接再開。
- 對局中想以玩家身分加入 → 變成觀戰者（`joined.note`）。觀戰上限 20（`spec_full`）；`allowSpectators=false` 時觀戰請求回 `error spec_off`。

## 4. 房間設定（settings.patch）

| 欄位 | 值 | 預設 |
|---|---|---|
| `mode` | `'race'`（競速）｜`'duel'`（對打，需 ≥2 人，其實 race 也需要 ≥2 人才能開） | `'race'` |
| `level` | `'baby'｜'easy'｜'normal'｜'hard'` | `'easy'` |
| `layout` | `'random'` 或 `Layouts.list()` 的 id | `'random'` |
| `theme` | `0..5` 或 `'random'`（開局時伺服器擲成 0..5 的整數） | `'random'` |
| `duration` | `120000｜180000｜300000`（毫秒） | `180000` |
| `maxPlayers` | `2..4`（不能低於目前已坐的人數，否則回 `error max`）；房間檢視裡對應 `max` | `4` |
| `publicRoom` | `true｜false`：false 時不出現在大廳列表、也不會被 `quick` 配到（用代碼／邀請仍可進） | `true` |
| `allowSpectators` | `true｜false` | `true` |
| `name` | 房間名稱（≤10 字） | `「<房主>的房間」` |

不合法的欄位會被忽略（其他欄位照常生效）。

## 5. 對局

### 5.1 開始

```
S→C { type:'start', cfg, slot, t0Wall, goIn, serverNow }
```

- `cfg`：`{mode, level, seed, layoutId, themeId, duration, players:[{name,dragon,kind:'human'|'ai',aiLevel?}]}`，players 依座位順序（真人與電腦混排，略過空位）；電腦的 `kind:'ai'`、`aiLevel` 給 HUD 顯示 🤖 與結算用；**直接拿去 `Match.create(cfg)`**。
  `layoutId` 可能是 `'random'`（`Rules.newBoard` 會用 seed 決定，所有人結果相同）。`themeId` 一定是 0..5 的整數。
- `slot`：你的操作席位（`cfg.players` 的 index）；觀戰者為 `-1`。
- `t0Wall`：伺服器時鐘（`Date.now()` 毫秒）上「對局時間 0」的時刻。`goIn`：這則訊息送出時距離 t=0 的毫秒（新開局固定 3000；中途收到的人是剩餘時間）。`serverNow`：送出當下的伺服器時鐘。
- **對局時間 mt** = 伺服器現在時間 − `t0Wall`（毫秒）。`mt < 0` 是倒數，輸入會被忽略。客戶端用 `serverNow` 與自己的 `Date.now()` 估時差，再由 `ev.mt` / `clock.mt` 校正。
- 開始時 phase 變 `countdown`，mt ≥ 0 後變 `playing`（會推一份 `room`）。
- 中途進來的人（晚到的觀戰者、斷線重連的玩家）收到 `start` 之後**緊接著** `sync`（§5.4），不重播歷史。

### 5.2 輸入與事件

```
C→S { type:'shot', a }       a：發射角度（百分之一度，1200..16800；伺服器會 clamp）
C→S { type:'swap' }          交換手上與下一顆
S→C { type:'ev', evs:[Event...], mt }
```

- **電腦席位**：伺服器代打。每個電腦在對局開始時以 `AI.createBrain(aiLevel, (cfg.seed + 977*(slot+1)) >>> 0)` 建一顆 brain（與單機 `game.js` 同公式），之後每次伺服器推進時間（`stepMatch`，每 50 ms 或有輸入時）呼叫 `AI.think(brain, board, dt, mode, ready)`（dt = 伺服器時鐘差），決定後走和真人完全相同的 `applyInput`（冷卻檢查 → `Match.input` → 廣播 `ev`）。所以客戶端只會看到一般的 `{e:'shot', s:<電腦 slot>, ...}`／`swap` 事件，對帳、`hash`、`sync` 都不用特別處理。倒數期間不動；對局結束、房間關閉時 brain 清除。電腦不會離場、不會被 `left`。時鐘可注入（測試用假時鐘）、亂數由 seed 決定，所以相同輸入流程得到相同事件序列。
- 每席位發射冷卻 **250 ms**（以伺服器收到的時間計）：太快的 `shot` 靜默丟棄；`swap` 冷卻 100 ms。觀戰者、倒數中、對局結束後的輸入全部靜默忽略。**客戶端請把發射間隔保持在 ≥ 260 ms。**
- 沒有單獨的 ack：你的 `shot` 變成 `ev` 裡的 `{e:'shot', s, a, t}` 廣播給**所有人（包含你自己）**。客戶端對每個 `ev.evs[i]` 依序呼叫 `Match.apply(m, ev)`（結果與動畫資訊由 `apply` 的回傳值取得）；不要自己先改盤面（要預測動畫可以用 `Rules.trace`，但盤面以事件為準）。
- `Event`（見 `match.js` 標頭）：`shot{s,a,t}`、`swap{s,t}`、`pend{to,from,id,n,at,t}`、`cancel{to,id,n,t}`、`land{s,id,n,t}`、`end{t,result}`。`t` 是對局時間。
- 一個 `ev` 批次可能含多個事件（例如一發 shot 造成 cancel／pend、時間推進造成 land），順序即套用順序。只有產生事件時才送。伺服器每 50 ms 推進一次時間（`land`、時間到的 `end`）。
- `ev.mt` 是送出時的對局時間，可用來校時。

### 5.3 對帳

```
S→C { type:'clock', mt }                         每 2 秒
S→C { type:'hash', seq, h:[Rules.boardHash(board) ...], mt }    每 2 秒
C→S { type:'resync' }
S→C { type:'sync', snap, mt }
```

- `hash.seq` 是伺服器 `m.seq`（套用過的事件總數）。因為訊息有序，收到 `hash` 時客戶端應已套用同樣多的事件：`m.seq === hash.seq` 時比對 `h`，不一致就送 `resync`；seq 不相等就略過這次。
- 任何時候都可以送 `resync`（例如客戶端例外、懷疑狀態不對）。

### 5.4 快照（sync）

`snap = { cfg, seq, boards:[Rules.snapshot(b)...], pending, reachedAt, lastAttacker, left, gid, over, result }`

還原：`m = MatchSnap.restoreAll(snap)`（`public/js/matchsnap.js`，瀏覽器可直接載入，掛在 `window.MatchSnap`）。還原後繼續套用之後的 `ev`，雜湊與伺服器一致（有測試保證）。

### 5.5 離場與結束

```
S→C { type:'left', slot, mt }        slot 的玩家離場（主動離開、被踢、斷線超過 30 秒）
S→C { type:'result', result }
```

- `left`：客戶端請直接 `m.left[slot] = true`（**不要**呼叫 `Match.playerLeft`，它會在本機產生 `end` 事件、讓 seq 失去同步）。如果這個離場導致對局結束，`end` 事件會跟在後面的 `ev` 裡。
- 結束：最後一批 `ev`（含 `end` 事件）之後送 `result{result}`（`result = m.result`：`{reason:'time'|'clear'|'left', ranks:[...], winner, mode, layoutName}`）。約 0.5 秒後房間回到 phase `'room'`，所有人 `ready=false`、房主不變（會推 `room`）。這段時間的 `rematch` 會在回房間時套用。
- 對局中的玩家離開後，座位會變成 `empty`（`slot` 的 `left` 為 true）；只剩 1 位玩家時對局照常進行到結束。有電腦在的房間，剩一位真人時電腦照樣對打（電腦席位不算「離場」）；`Match.playerLeft` 只有在所有真人都離場時才以 `reason:'left'` 結束（實際上此時房間已關閉）。

## 6. HTTP

| 路徑 | 回應 |
|---|---|
| `GET /health` | `{ok:true, game:'rainbow-bubble', uptime}`（Render health check；前端喚醒冷啟動用） |
| `GET /api/presence` | `{gameId:'rainbow-bubble', online, players, spectators, lobby, rooms, updatedAt}`（遊戲大廳的統一格式） |
| `GET /*` | 靜態檔（`public/`） |

CORS／WebSocket 來源：環境變數 `GAME_ALLOWED_ORIGIN`（逗號分隔；`*` 或留空 = 不限制）。
